# Postman collection — Full API Suite

`LN-Replica.postman_collection.json` + `LN-Replica.postman_environment.json`.

Generated by [`scripts/generate-postman-collection.ts`](../../scripts/generate-postman-collection.ts)
from a single declarative request list — same "generate an artifact from
one source of truth" philosophy as `scripts/generate-openapi.ts`. **Don't
hand-edit the collection JSON** — edit the generator and run
`npm run postman:generate`, then commit the regenerated file.

## Run it

1. Postman → Import both files.
2. Select the "LN Replica — Local" environment.
3. `docker compose up -d && npm run seed && npm run dev` (repo root) so
   `demo-client`/`demo-secret-change-me` exist and the API is listening on
   `:3000`.
4. Run the collection top-to-bottom (Collection Runner) — folders and
   requests run in dependency order; later ones depend on variables
   (`access_token`, `scorecard_id`, `report_id`, ...) set by earlier ones.

Or headless via [Newman](https://github.com/postmanlabs/newman):

```bash
npx newman run docs/postman/LN-Replica.postman_collection.json \
  -e docs/postman/LN-Replica.postman_environment.json
```

The whole collection is re-runnable against the same persistent
`demo-client` — every created resource uses a `{{$timestamp}}`-suffixed
name, and no assertion assumes a singleton resource (self/company/options)
is in a fresh, never-touched state. Verified stable across repeated runs.

## Live testing notes (this generator's own validation)

This collection was validated by actually running it with Newman against
a live `npm run dev` instance, not just generated and assumed correct.
That process caught three real bugs, since fixed:

1. **Production bug** — `POST /reports/{id}/actions/remote-check` re-run
   after completion returned the generic "report closed" code (1325)
   instead of the more specific "already completed" code (1313), because
   the generic guard in `runAction` ran before the remote-check-specific
   one. Fixed by reordering; the automated test for this path previously
   only asserted the HTTP status, not the error code, so it hadn't caught
   the misordering — that test now asserts the specific code too.
2. **Generator bug** — the JSON-path test-assertion helper used bare dot
   access (`.data.dob-verification`), which JavaScript parses as
   subtraction for any hyphenated key — and report action names are
   hyphenated (`dob-verification`, `otp-email-verification`, ...). Fixed
   by switching to bracket notation for every path segment.
3. **Test-authoring bug** — an early draft asserted `remote_check`
   defaulted to `true` on `demo-client`'s options singleton, which broke
   the moment that same persistent row got toggled by an earlier run —
   the same class of bug fixed earlier this session in
   `tests/integration/users.test.ts`. Fixed by asserting shape, not an
   assumed-fresh value, and using a set-then-check pattern instead.
